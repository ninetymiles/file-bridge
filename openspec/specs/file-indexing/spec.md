# file-indexing Specification

## Purpose
定义基于 SQLite 的多媒体文件元数据索引存储、SHA-256 去重机制以及离线归档后的“重建索引”指令维护规范。

## Requirements

### Requirement: SQLite 元数据索引表管理
系统 SHALL 在 `OUTPUT_DIR/metadata.sqlite` 中维护唯一的元数据索引表，记录发送者、接收日期与时间、原始文件名、本地保存文件名以及文件的 SHA-256 哈希值。

#### Scenario: 记录新文件元数据
- **WHEN** 新文件成功下载并保存到本地日期目录
- **THEN** 系统在 SQLite 数据表中插入一条包含发送者、时间、原始名、本地名与 SHA-256 的元数据记录

### Requirement: 基于哈希与磁盘文件实存的双重查重
系统 SHALL 在收到文件后首先计算 SHA-256，仅当 SQLite 索引中存在相同哈希且对应磁盘文件实际存在时，才判定为重复文件。

#### Scenario: 判定为重复文件
- **WHEN** 收到新文件计算其 SHA-256，在数据库中匹配到相同哈希值，且之前记录的磁盘文件确实存在
- **THEN** 系统放弃写入文件系统，向发送者回复“文件已存在，请勿重复发送”的提示

#### Scenario: 哈希曾存在但磁盘文件已被移走
- **WHEN** 收到新文件计算其 SHA-256，在数据库中匹配到相同哈希值，但之前记录的磁盘物理文件已不存在（已被归档移走）
- **THEN** 系统视为新文件重新写入当前日期目录，并更新或追加数据库索引记录

### Requirement: 索引一致性校验维护指令
系统 SHALL 支持用户通过文本指令触发索引一致性校验：遍历 SQLite 元数据索引表中的记录，核验每条记录对应的磁盘文件是否实际存在，并删除物理文件已缺失的记录。

该指令 SHALL 仅做单向的索引到文件的一致性校验与缺失记录清理：它 MUST NOT 扫描文件系统以补录未被索引的文件，MUST NOT 修改仍有效记录的内容，MUST NOT 读取文件内容或重新计算 SHA-256（仅核验路径存在性）。

本指令的回复文案属于展示层：规范仅约束回复须包含已清理记录数与剩余记录数两项信息要素，MUST NOT 锁定具体措辞。内部实现沿用 `rebuild_index` 作为方法名与命令标识，该命名仅作历史兼容，不构成对本指令"校验一致性、只清理不补录"语义的暗示。

#### Scenario: 触发索引一致性校验指令
- **WHEN** 用户在单聊或群聊中发送校验索引的文本指令
- **THEN** 系统遍历 SQLite 中的记录，核验每个文件在磁盘上是否存在，删除物理文件不存在的记录，并向发送者回复包含已清理记录数与剩余记录数的确认消息

#### Scenario: 校验不补录未索引文件
- **WHEN** 磁盘上存在未被 SQLite 索引记录的文件时执行该校验
- **THEN** 系统不将该文件补录进索引，仅清理已索引但物理文件缺失的记录

### Requirement: 启动时自动执行索引一致性校验
系统 SHALL 在服务启动流程中、SDK 连接之前，自动执行一次索引一致性校验，核验 SQLite 中每条记录对应的磁盘文件是否仍存在，删除物理文件已缺失的记录。校验完成后系统 SHALL 在控制台输出 INFO 级别日志，报告清理的记录数与剩余的记录数。该校验 SHALL NOT 通过机器人发送通知消息。

#### Scenario: 启动时自动执行索引一致性校验
- **WHEN** 服务启动流程开始，`MetadataStore` 初始化完成且尚未调用 `BotService.start()` 连接 SDK
- **THEN** 系统调用 `rebuild_index()` 核验磁盘文件实存性并删除缺失记录，随后以 INFO 日志输出清理记录数与剩余记录数

#### Scenario: 校验完成不发送机器人通知
- **WHEN** 启动时索引一致性校验完成
- **THEN** 系统仅在控制台打印 INFO 日志提示清理结果，不通过机器人向任何会话发送通知

#### Scenario: 空数据库或无陈旧记录时正常通过
- **WHEN** 启动时索引一致性校验执行完毕，数据库为空或无磁盘文件缺失的记录
- **THEN** 系统输出清理 0 条、剩余 N 条的 INFO 日志，继续后续启动流程（发送上线通知、连接 SDK），不报错不阻塞
