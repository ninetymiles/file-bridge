# Proposal

## Why

冷盘场景下，多图片群聊消息的处理耗时超过 60 秒，而 SDK 只有在 `process()` 返回后才发送 ACK；钉钉因此重投同一条消息，第二次处理命中 sha256 去重并回复「文件已存在，请勿重复发送」，与紧邻上一条「文件接收成功」自相矛盾。

线上日志已复现两次（11:34 两张图、13:37 三张图）：重投都精确发生在推送后 T+60s，而同样冷盘但 T+60s 内完成 ACK 的两条消息（04:01、05:11）没有重投。因此这不是偶发问题，而是「ACK 与处理耦合」导致的结构性必然。

## What Changes

- Dispatcher 收到回调后**立即**确认（返回 `AckMessage.STATUS_OK`），不再等待处理链结束。
- 处理链改为后台任务异步执行；该任务注册到现有在途任务集合，停机 drain 语义保持不变。
- 后台任务的未捕获异常必须被显式取回并记录，不允许静默丢失。
- 回复内容、层级裁决、两段式点评顺序、「单条入站消息回复不超过 2 条」等既有契约全部不变。
- 明确非目标：不做 `messageId` 幂等门。平台侧偶发重投（网络抖动）仍可能产生一次重复回复，本次只消除「必然越线」的结构原因。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `message-pipeline`: 新增「回调确认与处理解耦」要求（确认时机不得依赖处理时长，并明确停机收尾与异常兜底）。既有「Pipeline 流转模型」的回复合并与层级裁决行为不变，无需修订。

## Impact

- `app/handlers/message.py`：`PipelineHandler.process()` 改为立即确认并派发后台任务；新增任务完成回调（摘除跟踪 + 记录异常）。
- `tests/`：3 个测试文件共 36 处 `process()` / `_send()` 调用需要在断言回复前汇合后台任务（`test_drain.py` 的 4 处按停机语义单独适配）；新增测试内汇合助手。
- 不修改 SDK 调用方式、回复文案、配置项，不引入新依赖。
- 冷盘多图消息的 ACK 延迟从 60~62 秒降至毫秒级，同时消除重投带来的重复下载（实测单次约 17MB）。
