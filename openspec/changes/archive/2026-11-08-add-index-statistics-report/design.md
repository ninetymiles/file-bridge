# Design

## Context

见 `proposal.md` 的"为什么"。当前实现约束：

- `MetadataStore.init_db()` 只执行 `CREATE TABLE IF NOT EXISTS`，对已存在的旧表没有补列能力，也没有 schema 版本标记。
- 索引表没有媒体类型列；平台消息本身携带类型：单聊 `picture` / `video` / `file` 由顶层 `msgtype` 区分，`richText` 的图片段为 `type=picture`。
- 命令接入是目录 + 分发表模型，新增命令只需扩数据，不改匹配与分发逻辑。
- 所有 SQLite 调用都在线程内执行，异步接口沿用 `asyncio.to_thread`。
- 部署策略允许人工删除旧库后重建，因此本次不需要兼容 v0 结构。

## Goals / Non-Goals

**Goals:**

- 新增只读统计报告指令，回答用户数、类型分布、最近新增与当天情况。
- 索引表记录媒体类型，新记录准确，类型为空的记录仍可统计。
- 以 `PRAGMA user_version` 标记当前结构版本为 1；新库直接建成当前结构，其他版本显式失败。
- 保证不认识新列的旧版本服务仍能正常运行。

**Non-Goals:**

- 不提供 v0 结构兼容或自动升级；旧库由部署时人工删除后重建。
- 不提供降级脚本或向下迁移。
- 不回填类型为空的记录。
- 不做 schema 漂移检测或自动修复；版本标记是唯一权威。
- 不改变 `rebuild_index()` 的"只清理、不补录"语义。
- 不做定时统计推送（TODO 中的每日自动报告属于后续独立能力）。

## Decisions

### 1. 媒体类型入库时按 `msgtype` 写入，列为可空

`file_metadata` 新增 `media_type TEXT`，取值 `picture` / `video` / `file`。写入点只有 `MediaFileHandler` 一处：单媒体消息传 `msgtype`，`richText` 图片段固定传 `picture`。

选择理由：平台类型是权威值；按扩展名推断会把"以 `file` 发送的 `.mp4`"误判为视频。列为可空且不设默认值：旧版本服务不认识该列，插入时自动得到 `NULL`，从而保持共存。备选方案（新增独立类型表）需要额外的关联查询，对当前只有三个取值的场景没有收益。

### 2. schema 版本只有 1，拒绝一切不匹配

```
is_new_db = not os.path.exists(db_path)   # 必须在 sqlite3.connect 之前判断
conn = sqlite3.connect(db_path)
if is_new_db:
    BEGIN IMMEDIATE
    CREATE TABLE file_metadata (...含 media_type...)
    CREATE INDEX IF NOT EXISTS idx_file_sha256 ...
    PRAGMA user_version = 1
    COMMIT
else:
    version = PRAGMA user_version
    if version != 1:
        raise UnsupportedSchemaVersion(db_path, version, 1)
```

部署时人工删除旧库，因此不需要 v0 迁移，也不需要区分"新库已含列"与"旧库缺列"。版本 0 只有一个含义：未初始化、旧库或建库中断残留，一律拒绝并提示人工删除后重启。

新库判断使用连接前的文件存在性，而不是表或列探测：空文件、旧库、建库中断残留都会走"已存在"分支，被版本检查统一拒绝。这是 fail-fast 的取舍——不再自愈，但不会产生结构损坏。

未来变更的形态：`CURRENT_VERSION` 升为 2 时，接受版本 1 并执行 v1→v2 迁移，写入版本 2；版本 0 与高于 2 的值仍拒绝。当前没有 v2，因此不预先搭建迁移循环或迁移表。

原子性：Python `sqlite3` 默认只对 DML 隐式开启事务，DDL 会独立提交，因此建表与版本号写入必须用 `BEGIN IMMEDIATE` … `COMMIT` 显式包裹。若中断，事务回滚；残留文件会在下次启动时被版本检查拒绝。

### 3. 任何不受支持的版本都在启动阶段失败

版本为 0、大于当前版本或未来无法识别的值，统一抛出包含库路径、发现版本与支持版本的显式异常，不执行任何 DDL。理由：没有降级脚本；按其他结构继续运行可能静默写坏数据。

### 4. 统计查询用 SQL 聚合，只有类型为空的行走 Python 回退

- 用户数：`COUNT(DISTINCT sender_id)`。
- 类型分布：对 `media_type IS NOT NULL` 的行 `GROUP BY media_type`。
- 日期聚合：`GROUP BY date(created_at)`，取最大日期作为最近新增；日期数量决定单日/多日分支。
- `media_type IS NULL` 的行只取 `saved_path`，按扩展名映射到照片/视频/其他后并入分项。

不把全表读入内存，避免索引增大后报告成本线性上升。备选方案（全部行读入 Python 聚合）实现更简单，但会随规模退化。

### 5. 类型回退集合固定为代码常量

照片扩展名集合取常见图片格式（如 png/jpg/jpeg/gif/webp/bmp/heic/heif/tif/tiff），视频取 mp4/mov/m4v/avi/mkv/webm/3gp，其余计入其他。回退只影响统计，不写回数据库。

### 6. 报告渲染为纯函数，分支按日期数量收敛

输入为统计结果值对象，输出为文本：

- 日期数为 0：空状态提示。
- 日期数为 1：单个日期块，包含人数与照片/视频/其他分项（该日即全库，不重复总量）。
- 日期数大于 1：总量块（人数、总数、分项）+ 最近新增块（日期、当天人数、当天份数）。

命令回调只负责取数与调用渲染，匹配器与分发表保持不变。

## 启动行为矩阵

`CURRENT_VERSION` 当前为 1。未来升级时，把"必须等于 1"扩展为"1 到 CURRENT 可升级"，其余规则不变。

| 场景 | 启动时的处理 | 结果 |
|---|---|---|
| 库文件不存在 | `os.path.exists` 判定为新库；同一事务内建当前结构并写入版本 1 | 正常启动，版本 1 |
| 库文件存在，版本 1 | 只读取版本，不执行任何 DDL | 正常启动 |
| 库文件存在，版本 0（旧库、空文件或建库中断残留） | 抛出显式错误，提示删除库文件后重启；不修改库 | 拒绝启动 |
| 库文件存在，版本高于 1 | 抛出显式错误，不修改库 | 拒绝启动 |
| 旧服务（不读版本）连接版本 1 的库 | 建表语句空操作；插入不带 `media_type`，列可空 → 成功且值为 `NULL`；既有查询不受影响 | 正常运行；写入记录类型为空，由报告回退归类 |
| 未来版本 2 的库 + 当前只支持版本 1 的代码 | 版本高于代码 | 拒绝启动 |
| 建库事务中断 | 事务回滚，可能留下版本 0 的文件；下次启动按版本 0 拒绝 | 需人工删除后重启 |
| 库文件不存在且目标位置不可写 | 建库失败 | 启动失败（fail fast） |

要点：版本 0 不再代表"待升级的旧库"，而是"无效或未管理的库"；只接受恰好等于当前版本的值。旧版本服务的兼容性只对**可空新增列**成立，这是后续迁移必须遵守的约束。

## Risks / Trade-offs

- [破坏性重置] → 索引中的 sender/原名映射与 SHA-256 去重历史丢失；磁盘媒体文件保留，但 `rebuild_index()` 不会重新收录，统计报告从空开始，直到有新投稿。这是换取启动逻辑简单的代价。
- [版本 0 残留需人工处理] → 建库中断或遗留旧文件会拒绝启动；错误信息必须给出"删除库文件后重启"的明确指引。
- [旧服务持续写入类型为空的记录] → 报告端回退归类，数据不丢；如需彻底准确，需停止旧服务。
- [回退推断与平台类型存在偏差] → 新记录使用平台类型；回退只用于类型为空的记录，偏差已接受并在规范中说明。
- [版本号被人工篡改] → 版本标记视为权威，不做结构复核；结构与版本不一致会在写入或查询时显式失败，而不是静默。
- [`created_at` 为服务器本地时间，无时区信息] → 日期边界按服务器本地时间计算；与既有行为一致。
- [`sender_id` 缺失时记录为 `unknown`] → 会作为一位用户计入；本次不改变身份口径。

## Migration Plan

1. 部署前停止服务。
2. 备份或直接删除 `metadata.sqlite` 及同目录的 `-wal`、`-shm` 文件。
3. 启动服务：首次启动创建当前结构并写入版本 1。
4. 验证：统计报告返回空状态说明索引已重置；新投稿入库后媒体类型正确。
5. 回滚：发布前的旧服务可运行在版本 1 的库上（新增列为空），但其写入记录类型为空；若未来库已被更高版本升级，回滚前需恢复备份。
