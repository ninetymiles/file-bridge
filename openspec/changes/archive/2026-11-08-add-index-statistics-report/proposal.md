# Proposal

## Why

当前索引只保存发送者、时间、路径、哈希等原始记录，没有任何媒体类型信息，无法回答"有多少用户、照片/视频/其他各多少、最近哪天新增"这类问题；管理员只能直接连 SQLite 手工查询。本次在聊天指令体系内新增只读的统计报告命令，并补齐索引中缺失的媒体类型。

引入 `media_type` 意味着索引表发生第一次结构演进。当前数据库没有 schema 版本标记，`CREATE TABLE IF NOT EXISTS` 对旧表是空操作。本次采用破坏性重建策略：部署时人工删除旧库，新库直接建成当前结构并标记为 v1；启动时只接受与代码一致的版本；不提供旧结构自动升级。这样可以用人工删除换取启动逻辑的最小化。

## What Changes

- 索引表新增可空列 `media_type TEXT`，取值 `picture` / `video` / `file`，入库时按消息的 `msgtype` 写入；`richText` 图片段记为 `picture`。
- 引入 `PRAGMA user_version` 版本标记，当前 schema 版本为 1：
  - 库文件不存在：创建当前结构并写入版本 1，两者在同一事务内完成，不执行任何迁移。
  - 库文件已存在：仅接受版本 1；版本为 0（旧库、空文件或建库中断残留）或高于 1（或其他不受支持的值）时，启动阶段显式报错并拒绝启动，不修改数据库。
  - 不提供 v0 兼容与自动升级；旧库由部署时人工删除后重建。
  - 未来结构变更从 v1 起依次增加 v2、v3，启动时按版本顺序补齐。
- 新增 `index_report` 命令及陈述式触发短语（统计报告、生成统计报告、索引统计、统计索引、投稿统计、索引报告、分析索引、分析文件索引），通过命令目录与分发表接入，不修改匹配与分发逻辑。
- 新增只读统计聚合与报告渲染：总用户数、总文件数、照片/视频/其他分项、最近新增日期、当天用户数与份数。
- 报告输出规则：空索引只提示无记录；索引只包含一天时输出单块报告并保留照片/视频/其他分项，不再重复总量；跨多天时输出总量块与最近新增块。
- 媒体类型为空的记录在统计时按 `saved_path` 扩展名回退归类，不回填数据。
- **兼容性**：`media_type` 为可空列，不设默认值与约束，旧版本服务仍可启动与插入，其新写入记录类型为空。

## Capabilities

### New Capabilities

- `index-report`: 定义索引统计报告的触发指令、统计维度、单日合并规则、空索引回复与空类型记录回退。

### Modified Capabilities

- `file-indexing`: 元数据索引表新增媒体类型字段；新增数据库 schema 版本标记与启动时版本校验的行为要求；明确不提供旧结构自动升级，旧库由部署时人工删除；索引一致性校验的"只清理不补录"语义保持不变。

## Impact

- 代码：
  - `app/services/metadata_store.py`：建表结构、初始化时的版本校验、插入参数、统计聚合查询。
  - `app/handlers/message.py`：入库时传入 `media_type`。
  - `app/services/command_matching/catalog.py`、`app/services/command_matching/__init__.py`：新增命令 id 与触发短语。
  - `app/main.py`：新增分发表回调。
  - 新增报告渲染模块（纯函数，便于单测）。
- 数据：部署时必须人工删除旧的 `metadata.sqlite`（连同 `-wal`、`-shm`）。索引中的 sender/原名映射与 SHA-256 去重历史随之丢失；磁盘上的媒体文件保留，但不会由 `rebuild_index()` 重新收录，统计报告从空开始，直到有新投稿。
- 外部：任何直接读取 `metadata.sqlite` 的下游可用新增列；旧服务与新结构共存时，其写入行的类型为空，由报告端回退推断。
- 依赖：无新增第三方库。
