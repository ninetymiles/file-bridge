# Design

## Context

现状见 `app/handlers/message.py`：`_handle_rich_text` 在逐张落盘时立刻为每张图 `batch.add(index, path)`，`_ReviewBatch` 并发跑完全部点评，`_format_reviews` 在点评条数大于 1 时加「图N：」前缀。批的总时限从第一次请求起算，合并窗口在全部图片处理完之后才开始计时。

本设计只改点评的选取与呈现，不改点评服务、启动探测、存储预热与模型预热。

## Goals / Non-Goals

**Goals:**

- 一条消息至多一条点评，且多图消息必须能说明是对第几张图的点评。
- 选取过程不引入任何额外等待，也不新增状态。
- 保持既有的两段式投递（15 秒窗口 / 补发）与“最多 2 条回复”的上限。

**Non-Goals:**

- 不做随机抽取，不做“抽不到就换一张”的重抽，也不做顺延。
- 不改 `PhotoReviewer` 的请求形态、超时策略与降级语义。
- 不处理“单聊直发多图被拆成多条 `picture` 消息”的场景：那是多条独立消息，各自仍是单图消息，不带图号。

## Decisions

### 决策 1：选择规则是“第一张保存成功的图片”，按图片段原始顺序

循环中第一次遇到 `status == "saved"` 的图片即作为点评对象；重复图片与失败图片自然被跳过，不消耗点评机会。该规则不需要预先知道候选集合，因此不等下载、不需要候选列表，也天然确定（无随机源）。

替代方案：随机抽一张、不重抽。代码只多一行抽签，但会把点评机会浪费在重复图上（抽中重复图即本条无点评），且测试必须为每个多图用例注入随机源。

替代方案：从“全部保存成功的图片”中随机抽取。必须等循环结束才知道集合，点评与下载不再重叠，且需要候选列表，否决。

替代方案：顺序首张 + 失败顺延。覆盖率略高，但需要候选列表、游标、串行重试，以及区分“返回空（可顺延）”与“仍在跑（不可顺延）”，属于为低概率场景增加的控制流，否决。

### 决策 2：一次点评，不重试、不顺延

第一张保存成功的图片若点评未取得有效文本，本条消息就没有点评。语义简单：要么「图N：…」，要么没有点评。

替代方案：失败后尝试下一张。仅能覆盖模型偶发空输出与单张图解码失败这类低概率事件；系统性失败（网关不可达、鉴权错误、模型不在清单）换图同样失败。收益不足以抵消控制流成本，否决。

### 决策 3：图号由“消息的图片段数量”决定，而不是由点评条数决定

`_format_reviews` 现在的入参是 `dict[int, str]`，条数天然为 0 或 1，无法再据此判断是否需要编号。改为把“消息是否含多个图片段”作为渲染条件传入：多图消息一律渲染 `图{原始序号}：{文本}`，单图消息直接输出文本。

替代方案：永远加图号。会让本来清晰的单图回复变成「图1：…」，否决；也与既有「单张图片的点评不加图号」的意图冲突。

### 决策 4：复用 `_ReviewBatch` 的既有布尔语义实现“只点评第一张”，不新增状态

`_ReviewBatch.__bool__` 在尚未 `add` 时返回假、`add` 后因任务已创建返回真，因此循环内的条件写成 `if not batch: batch.add(...)` 即可表达“首次遇到保存成功的图片”，无需新增标志变量。`wait(15s)`、`finish()`、补发路径全部保持原样。

替代方案：新增 `first_saved_index` 之类的标志。功能等价却多一处状态，否决。

### 决策 5：首张图片的点评在它落盘时立刻起跑

抽签已不存在，处理到该图并保存成功时即可 `batch.add`，与它之后图片的下载并行。合并窗口仍以“全部图片处理完”为计时起点，语义不变。

## Risks / Trade-offs

- [点评对象固定为第一张保存成功的图] → 用户每次看到的都是「图N：」，缺少变化。这是可预期性的代价；若产品要求点评对象有变化，需改回随机方案（决策 1 的替代方案）。
- [首张点评失败即整条消息无点评] → 接受。系统性原因换图也无用，低概率的单图原因不值得引入重试控制流。
- [挂起请求没有兜底换图] → 点评客户端 `read=None`，一次请求可能挂到 60 秒总时限才被取消。接受该限制：没有重试就没有这个分支。
- [多图消息的首条点评可能较晚] → 首张图片若排在消息末尾、或点评请求较慢，会走“先发保存结果、再补发点评”的两段式，仍受 15 秒窗口与 60 秒总时限约束。
- [测试契约变更] → 多图点评的既有用例与新语义冲突，必须改写为“单次请求 + 图号 + 重复图跳过”，不能保留旧断言。

## Migration Plan

单次发布，无数据迁移、无配置项变更。回滚即回退代码。
