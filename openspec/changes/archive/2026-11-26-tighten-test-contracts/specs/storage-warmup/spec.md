# Spec Delta

## MODIFIED Requirements

### Requirement: 消息入口的存储预热与超时提示

系统 SHALL 在每条消息进入处理链之前执行一次存储预热：在事件循环线程之外发起一次对存储卷的写探测，同时启动 3 秒计时。探测在 3 秒内完成时，系统 MUST NOT 发送任何提示，处理链直接继续；计时先到期时，系统 SHALL 立即向当前消息的发送者回复一条固定措辞的唤醒提示，随后等待探测完成再继续处理。无论是否发送唤醒提示，处理链的既有回复裁决（意图合并或兜底回复）SHALL 均正常执行，唤醒提示不替代、不抑制任何最终回复。探测抛出异常时，系统 SHALL 向发送者回复一条固定措辞的存储不可用提示并终止该消息的处理，并按正常回调确认处理，MUST NOT 向上层 SDK 传播为未捕获异常。3 秒阈值与提示措辞 SHALL 固化在系统中，MUST NOT 新增运行时配置项。

#### Scenario: 热盘快速就绪时静默继续

- **WHEN** 存储卷处于就绪状态，写探测在 3 秒内完成
- **THEN** 系统不发送唤醒提示，直接进入处理链，用户仅收到既有裁决后的最终回复

#### Scenario: 冷盘唤醒超时时先发提示再继续

- **WHEN** 存储卷处于休眠状态，写探测在 3 秒内未完成
- **THEN** 系统在 3 秒届满时立即向发送者回复一条固定措辞的"正在唤醒存储服务"提示，等待探测完成后继续处理链，并在完成后正常发送最终回复；发送者先后收到两条消息

#### Scenario: 探测异常时回复不可用提示

- **WHEN** 写探测因存储卷不可达、权限不足等原因抛出异常
- **THEN** 向发送者回复固定措辞的存储不可用提示，确认回调，该消息不再进入处理链；异常不向 SDK 传播

## REMOVED Requirements

### Requirement: 预热探针的确定性触达

**Reason**: 该要求包含「探测先于首条日志完成」场景，以日志输出作为顺序载体，属于实现约束；其余探针约束需要保留并重写为不含日志的顺序表述。

**Migration**: 探针的真实写、拒绝缓存假成功、工作线程执行三条约束迁移至新增要求「预热探针的确定性与事件循环不阻塞」；顺序由「消息入口的存储预热与超时提示」中的「进入处理链之前」保证。

### Requirement: 冷盘唤醒期间的 LLM 预热

**Reason**: 要求文本与场景把「失败只输出单行 WARNING、成功不占 INFO」写成了契约，属于日志实现细节。

**Migration**: 触发条件、fire-and-forget、token 上限、in-flight 去重与失败不影响点评等行为迁移至新增要求「冷盘唤醒期间的模型预热」。

## ADDED Requirements

### Requirement: 预热探针的确定性与事件循环不阻塞

探针 MUST 为对 `OUTPUT_DIR` 所在存储卷的真实写操作：覆写该目录下的活动文件 `.activity`，写入当前时间戳，并在返回前完成刷盘（flush 与 fsync），确保写请求到达存储服务端并强制处于休眠状态的磁盘完成唤醒。系统 MUST NOT 以目录或文件存在性检查（如 `os.path.exists`）作为探针——该类元数据查询可能命中操作系统或网络文件系统客户端的缓存，在磁盘休眠时假成功而不触发唤醒。探针的阻塞式磁盘访问 MUST 在工作线程中执行，使唤醒期间的事件循环与 3 秒计时器不被阻塞。

#### Scenario: 冷盘被一次真实写请求唤醒

- **WHEN** 存储卷休眠，系统执行预热探针
- **THEN** 探针向 `.activity` 的写入与刷盘请求到达存储服务端并触发磁盘唤醒，随后同一消息处理中的下载落盘与 SQLite 访问不再承担唤醒等待

#### Scenario: 唤醒等待不阻塞事件循环

- **WHEN** 探针因冷盘唤醒阻塞约 30 秒
- **THEN** 3 秒计时器仍能准时到期并触发唤醒提示的发送，事件循环上的其他并发消息处理不被探针阻塞

### Requirement: 冷盘唤醒期间的模型预热

当消息入口的存储预热因冷盘超过 3 秒、且启动健康检测已确认 API 可达并包含配置模型时，系统 SHALL 在发送唤醒提示的同时，以 fire-and-forget 方式向点评网关发起一次文本 chat 请求，输出 token 上限 SHALL 为 1，以提前触发模型加载。该请求 MUST NOT 被等待完成后再发送唤醒提示或继续等待磁盘；MUST NOT 参与点评启用或禁用决策。并发冷盘消息产生的重复请求 SHALL 通过 in-flight 去重限制为至多一个未完成请求。启动健康检测未通过或点评未启用时 MUST NOT 发起该请求。

#### Scenario: 冷盘唤醒时并发触发模型加载

- **WHEN** 存储探针在 3 秒内未完成，且启动健康检测已通过
- **THEN** 系统在发送"正在唤醒存储服务"提示的同时发起一次 LLM 预热请求，唤醒提示不被该请求延迟，磁盘等待继续正常进行

#### Scenario: 热盘快速就绪时不预热

- **WHEN** 存储探针在 3 秒内完成
- **THEN** 系统不发送唤醒提示，也不发起 LLM 预热请求

#### Scenario: 预热失败不影响点评与后续处理

- **WHEN** LLM 预热请求返回非 2xx、超时或网络异常
- **THEN** 点评能力保持原启用状态，磁盘等待与后续消息处理不受影响，进程不因该失败退出

#### Scenario: 健康检测未通过时不预热

- **WHEN** 启动健康检测失败（API 不可达或配置模型不在清单中）
- **THEN** 冷盘唤醒时系统只发送唤醒提示，不发起 LLM 预热请求

#### Scenario: 并发冷盘消息不重复加载

- **WHEN** 同一冷盘唤醒期间有多条消息同时进入处理链
- **THEN** 至多存在一个未完成的 LLM 预热请求，后续消息不会叠加新的预热请求

### Requirement: 唤醒提示的发送路径不含本地 I/O

发送唤醒提示与存储不可用提示时，系统 MUST NOT 在 DingTalk 发送动作之前执行任何本地磁盘写入（含同步日志写入）；提示的本地记录 SHALL 发生在发送完成之后。目的是避免冷盘下的日志 I/O 延后用户可见提示。本要求由实现注释与代码评审保证，不建立自动化测试。

#### Scenario: 冷盘下提示先送达再记录

- **WHEN** 存储探针超时且磁盘仍处于唤醒过程中
- **THEN** 唤醒提示 SHALL 在探测等待期间完成发送，其本地记录在发送完成之后执行
- **THEN** 提示的送达时间 MUST NOT 因本地日志写入而延后
